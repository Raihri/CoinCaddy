### Known gaps and risks

- (At the end of Prompt 02) tests wrote into the development database, which is why it contains older test events. Prompt 03 moved tests to a separate `smecopilot_test` database.
- Successful reads (profile, member list, audit page) are not recorded; only sensitive operations and refusals are. Requests with no session (401) are not recorded because there is no actor.

- No IP address or request ID is stored. There is no retention or export policy for audit data.
- Denied and refused attempts commit their audit event before the error response. A failure while writing that event turns the refusal into a 500, so the request is still refused.
- No approvals or action execution (Prompt 15/17). The approval inbox card is a placeholder.

### Known gaps and risks

- The rules and thresholds (14-day duplicate window, 3x median, 60% / BDT 50,000.00 split limit, 85% similarity, 3- and 7-day settlement windows) are fixed for `fraud-rules-v1`. They have not been tuned on real data, and the split rule runs only for BDT.
- Payee-based rules need a payee on the ledger row (a mapped payee column) or from a bill. Imported rows without a payee are checked for duplicates only by reference.
- The rules run when a payment is proposed, approved, or released, when a destination is recorded, or on "Run checks". There is no schedule, and nothing is sent outside the app.
- Destinations are whatever the owner or bookkeeper records; nothing checks with the bank. The keyed hash is only as private as `DESTINATION_HASH_KEY`, which is a local placeholder.
- "Independent verification" is what the reviewer records (method, contact source, date); nothing calls the payee.
- The cash outcomes are bounds on today's inputs with simple timing assumptions (paid or recovered tomorrow), not a forecast of recovery.
- A hold only stops approval, release, and (since Prompt 17) a sandbox run in this app. There is no real payment execution.

### Known gaps and risks

- Everything is a sandbox: no message, payment, application, or packet leaves the machine, and no live credentials exist. The mock's idempotency store is in memory, so a mock restart forgets it. The app's own tables still prevent a second run of a proposal that already has an outcome.
- The HTTP call to the mock is made while the proposal row is locked inside the database transaction (5-second timeout). This is fine for a local sandbox; a real integration would need an outbox.
- After a "failed" (no answer), only a retry with the same key can finish the action. If the key is lost (another browser tab), the proposal stays without a final outcome; a new proposal is needed.
- A rejected outcome is final for that proposal; a corrected action needs a new proposal.
- Packet sharing has an adapter and a mock endpoint, but no proposal type yet (Funding Passport, Prompt 20). Reminders go to the customer by name only; contact verification is Prompt 18.
- A payment requires a recorded destination, and it goes to the supplier's current destination at run time (a change after approval is caught by the Fraud Monitor hold, as tested).

## What can be claimed now

A runnable local development foundation exists: database with a versioned schema, an API with health checks, a mock external-service boundary, a synthetic fixture with independently checked money values, and a responsive application shell.

Local demo sign-in with owner/bookkeeper/staff roles is enforced in the API, and unknown actions are denied. The tested scenarios show that staff cannot change owner settings and that changing a business ID (including for exports) reveals nothing about another business. This is API-level enforcement tested on these scenarios only, not a security certification.

Sensitive operations and refused attempts are recorded in an append-only, hash-chained, redacted audit trail. Owners and bookkeepers can read their business's audit history and nobody else's.

An owner can create and edit a business profile (name, jurisdiction, base currency, timezone, reserve in integer minor units, account labels). Strict server-side validation, owner-only edits, stale-edit protection, and audit events were all tested.

Bank and wallet statements can be imported safely from CSV/XLSX. Unsafe or ambiguous files are rejected, rows are staged with per-row errors, and possible duplicates must be reviewed. Selected rows are then posted exactly once to an append-only ledger. Staged rows are never treated as cash.

Account balances can be reconciled against statement anchors with declared source coverage, restricted funds, and own-account transfer pairing. A zero residual is never treated as proof of completeness, and stale or missing balances are never added to spendable cash. Customer invoices and supplier bills keep their original terms, with exact outstanding amounts after payments and reversals, and concurrent over-allocation is refused.

A cash-basis operating summary (not an audited P&L) ties every figure to its source records, and it was checked against the independent fixture. A 13-week Cash Outlook with expected and cautious paths is calculated from frozen, hash-verified input snapshots, and its exact path values were checked against a hand-worked fixture.

Deterministic alerts (reserve breach, overdue invoice, unusual outflow, repayment pressure) are shown on the Overview with their date, amount, cause, severity, and supporting record IDs, and repeated runs do not duplicate them. They run only on request; nothing is sent externally.

A proposed payment can be checked in four scenarios on one frozen snapshot, with exactly one decision state (within reserve under stated assumptions, reserve shortfall, or more information needed); known breaches stay visible and material unknowns block a positive result. Reports are saved and never initiate a payment. For each saved review, a ranked queue lists the missing, stale, or disputed records that could change it, with bounded best/worst effects only where the record has an amount; it never resolves evidence or changes the decision.

Illustrative financing products can be filtered by documented eligibility, costed exactly, and tested on the cash forecast, with exclusion reasons and the source and date of every term; they are labelled potential matches, never approvals.

For a payment that would breach the reserve, a Rescue Plan compares collecting an overdue invoice, moving a discretionary bill (only with a documented supplier permission), an illustrative financing match, and a combination on the same frozen forecast, and recommends one only when it closes the gap; it makes proposals only.

For a selected illustrative product, Financing Readiness shows each published condition and document as present, missing, or uncertain, with its source or verification step and concrete improvements. A check can only be "ready" when nothing is missing or uncertain (enforced in code and in the database). It calculates no approval probability or score, uses no personal traits, is separate from the match ranking, and submits nothing.

Proposed external actions (an invoice reminder, a sandbox supplier payment, a financing application) are stored immutably with their exact payload, tier, required role, expiry, and hash. T2 needs an explicit owner approval; T3 also needs owner re-authentication, a documented verification, and a second reviewer. Authorization, payload integrity, expiry, and the source records are re-checked before an action is marked executable, in the API and again by database rules. Staff denial, owner approval, expired approval, and tampered-payload rejection were tested.

A Transaction Fraud Monitor applies versioned rules (duplicate payment, unusual payee amount, split payments near a limit, lookalike payee, changed destination details, paid without settlement). It raises suspected-activity flags, never fraud verdicts, each with the compared record IDs and the rule's reason. For a material unresolved flag it shows two bounded cash outcomes on the Cash Outlook inputs. A flagged proposed sandbox payment is held: it cannot be approved or released (enforced in the API and in the database). A destination change is cleared only after independent verification by someone other than the person who recorded it. Reviewers confirm, clear, or defer with a reason, and the original records are never changed. Destination numbers are stored and audited only as their last four digits.

An approved and released proposal can be run once in the sandbox through its own mock adapter (reminder send, application submission, payment initiation; packet sharing is ready for a later proposal type). Approval, business scope, payload hash, expiry, the source records, and any fraud hold are checked again just before each run, in the API and by database triggers. Idempotency keys give a retry the stored outcome without a second call, and every attempt is logged with a timestamp and redacted request and result. An approved action, a denied unapproved action, a blocked fraud-held action, and an idempotent retry were tested. There is no real payment integration, messaging provider, or lender connectivity.
